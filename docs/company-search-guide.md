# 기업 검색 구현과 다음 AI 엔지니어링 단계

> 후속 구현: OpenAI RAG·임베딩·SQLite·근거 검토가 추가되었습니다. 현재 상태는 [RAG 구현 가이드](rag-build-guide.md)를 참고하세요. 아래는 해당 단계의 기록입니다.


작성: 2026-09-16. 아래 완료 항목과 계획 항목은 구분한다.

## 이번에 완성한 사용자 흐름

기업 검색 → 한국/미국 필터 → 기업 선택 → 연간 재무 수치 및 공시 링크 확인 → 해당 기업에 질문.

삼성전자·네이버·쿠팡·애플·엔비디아의 실제 공급자 데이터를 확인했다. 삼성전자 검색/선택/2025년 질문 및 애플로 전환은 브라우저에서도 확인했다. API 인증키는 서버의 `.env`에서만 읽고 프론트로 반환하지 않는다.

## 코드를 읽는 순서와 이유

1. `frontend/src/main.jsx`의 `CompanyPicker`: 입력 후 250ms 대기하고 `GET /api/companies?q=...&market=...` 호출. 입력이 바뀌면 이전 검색을 취소하고 이전 결과의 반영을 막는다. 이는 답변 품질과 별개인 비동기 상태 관리 문제다.
2. `providers/registry.py`: 이름/종목코드/일부 한국어 별칭으로 목록 검색. 내부 ID는 `DART:005930`, `SEC:AAPL`처럼 공급자를 포함한다. 화면의 기업명 문자열을 API 식별자로 직접 쓰지 않는다.
3. `main.py`의 `company_data`: `GET /api/company-data/{company_id}`. 등록된 ID만 수집 서비스에 전달하고, 프론트에 필요한 수치/통화/기간/출처를 반환한다. 이전 `/api/companies/CPNG/...` 경로는 기존 쿠팡 화면 호환용으로 남아 있다.
4. `providers/service.py`의 `load_financials`: 회사별 JSON 캐시(24시간)를 확인한 뒤 공급자를 선택한다. 같은 프로세스에서는 회사별 잠금으로 중복 수집을 줄인다. 다중 서버 환경의 분산 잠금은 아직 없다.
5. `sec_company.py` / `dart_company.py`: 외부 응답을 공통 레코드로 변환한다. 이 단계의 책임은 데이터 수집과 해석 가능한 구조로의 변환이다. LLM을 사용하지 않는다.
6. `providers/service.py`의 `summary`: 통화·기간·중복 계정을 확인하고 Python Decimal 기반 함수로 비율을 계산한다. 표의 표시 단위만 프론트에서 KRW는 억 원, 그 외 통화는 백만 단위로 변환한다.
7. `chat.py`: `company_id`를 명시적으로 받아 질문을 도구에 연결한다. 현재 정규식 기반 라우터이며 LLM Agent가 아니다. 다른 기업을 명시한 질문은 선택 변경을 안내한다. 별칭 인식은 완전한 개체 인식 모델이 아니다.

회사 변경 시 채팅을 비우고 진행 중인 응답을 취소한다. 서버 작업은 브라우저 취소 후에도 캐시를 마무리할 수 있지만, 프론트의 실행 번호와 취소 플래그가 이전 기업 응답의 화면 반영을 막는다.

## 시니어 리뷰에서 먼저 확인할 것

- 출처 식별: 종목코드는 회사 자체가 아니다. 미국은 SEC 제출 정보의 현재 티커로 검증한다. 한국은 종목코드를 DART 고유번호로 변환하고 응답 기업번호를 확인한다.
- 기간: 애플 2025 회계연도 종료일은 2025-09-27, 엔비디아의 최신 확인 자료는 2026-01-25 종료다. 모든 수치를 달력 연도 1~12월로 해석하면 안 된다. SEC는 실제 시작/종료일과 연간 길이를 검증한다. DART는 API의 사업연도 라벨을 표시하며 정확한 시작/종료일은 현재 레코드에 없다.
- 기준 혼합: DART는 연결(CFS)만 요청한다. 연결이 없을 때 별도(OFS)로 몰래 대체하지 않는다. SEC는 기업 전체 표준 XBRL 태그를 사용한다.
- 공시 버전: SEC는 최근 보고 기간의 마지막 연간/수정 공시를 선택한다. 해당 공시에 표준 수치가 없으면 이전 공시로 조용히 대체하지 않는다. DART는 최근 완료된 2개 사업연도 중 조회되는 사업보고서를 사용한다. 현재 분기 실적은 범위 밖이다.
- 누락과 충돌: 없는 값을 0으로 채우지 않는다. 매핑 충돌은 제외하고 경고한다. 금융업이나 기업 전용 계정은 추가 지원이 필요하다.
- 비밀정보: 인증키가 담긴 요청 URL을 로그/응답/원문 파일에 저장하지 않는다. 외부 오류는 정리된 메시지로 반환한다.
- 검색/계산/생성의 구분: 재무 API의 숫자, 본문 검색 후보, LLM이 만든 해석을 같은 신뢰 수준으로 취급하지 않는다.

## 현재 지원 범위와 남은 일

| 구분 | 현재 상태 |
|---|---|
| 기업 이름/종목코드 검색 | 구현, 일부 미국 기업 한국어 별칭 포함 |
| 한국 목록 | KRX 목록 스냅샷 2,800개 항목 |
| 미국 목록 | 공개 SEC 목록 미러 스냅샷 10,142개 종목 항목; 최신 전체 목록 보장 안 함. ETF/여러 주식 종류 등 포함 |
| 미국 기업 신원 | 선택 시 SEC 공식 submissions API로 티커 검증 |
| 연간 수치 | 지원 표준 태그의 매출·영업이익·영업현금흐름 및 비율 |
| 공시 본문 검색 | 쿠팡 2025 10-K만 색인 완료; 다른 회사로 검색 결과를 재사용하지 않음 |
| LLM 답변, 임베딩, Agent | 미구현. `.env` 필드만 준비됨 |
| Ontology, Property Graph, SQL DB | 미구현. 현재 JSON 파일 저장 |
| 대화 기억, 기업 간 비교, 분기, 주가 | 미지원 |
| 기업 목록 자동 갱신 | 미구현. 스냅샷 출처 메타데이터는 `company-registry.json`에 보관 |

목록에 검색된다는 사실과 재무제표를 정상 분석할 수 있다는 사실은 다르다. 모든 회사 지원 완료라고 표현하지 않는다.

## 다음 구현 순서: 채용 요건을 실제 기능으로 증명

### 1. 여러 기업의 RAG와 Prompt Engineering

- 기능: 삼성전자/애플 등 선택한 기업의 보고서를 수집·문단화하고, 출처를 인용해 질문에 답한다.
- SQL: 회사·공시·문단·수집 상태를 SQLite 테이블로 저장하고 기본키/외래키/중복 처리/트랜잭션을 배운다. 원문 파일과 메타데이터 저장을 나눈다.
- 검색: 현재 BM25를 기준선으로 유지하고 임베딩 검색과 비교한다. 먼저 company_id, filing_id, 기간으로 범위를 제한한다.
- 프롬프트: 질문·검증된 숫자·문서 근거를 분리한다. 근거가 없는 설명은 유보하고, 문서 내부 지시문을 명령으로 따르지 않게 한다.
- 완료 기준: 기업이 다른 근거가 섞이지 않고 인용이 원문에 존재한다. 정답 근거가 없는 질문에서 무리하게 답하지 않는 평가를 포함한다.

### 2. LLM Agent Architecture

- 도구: `get_financials`, `calculate_metrics`, `search_disclosures`를 명확한 입력/출력 스키마로 정의한다.
- 워크플로: 질문 분석 → 도구 선택 → 결과 검증 → 답변. 예측 가능한 처리는 고정 흐름으로 두고 필요한 선택만 LLM에 맡긴다.
- 검토 포인트: 도구 실패/재시도, 호출 수와 비용 상한, 잘못된 기업 ID, 누락 데이터, 실행 로그.
- 완료 기준: 질문에 따라 필요한 도구를 호출하고 숫자 계산을 LLM의 추측에 맡기지 않는다. 현재 규칙 기반 라우터와 실패 유형을 비교한다.

### 3. Ontology Modeling과 Property Graph

- 먼저 지식 구조: Company, Filing, FinancialFact, Metric, Period, Evidence를 정의하고 각 타입의 ID·속성·제약을 Markdown에 기록한다.
- 핵심 관계 예: Company → FILED → Filing → REPORTS → FinancialFact → MEASURES → Metric. FinancialFact는 Period 및 원문 Evidence와 연결한다.
- 숫자를 단순히 Company의 revenue 속성 하나로 저장하지 않는다. 기간·통화·연결 구분·수정 버전이 달라질 수 있기 때문이다.
- Property Graph에 적재한 뒤 “이 수치의 출처가 어느 공시이며 어느 기간·범위에 해당하는가?”를 관계 탐색으로 답한다.
- 검토 포인트: 온톨로지(의미/제약 설계), 그래프 DB(저장/질의), Agent 실행 그래프(제어 흐름)는 서로 다른 개념이다.
- 완료 기준: SQL로 충분한 질문과 관계 탐색이 유리한 질문을 비교하고, 그래프 도입 이유를 결과로 설명한다.

### 4. 평가·운영·인터뷰 준비

- 검색 적중률, 인용 정확도, 숫자 정확성, 답변 유보, 도구 호출 성공률, 지연/비용을 별도 측정한다.
- Git 저장소를 정리하고 기능별 변경과 리뷰 기록을 남긴다. 실제 키·원문 대용량 파일을 추적하지 않는다.
- Markdown ADR에 선택 이유/대안/한계/검증 결과를 남긴다. README에는 실행 방법과 실제 지원 범위를 유지한다.
- 인터뷰에서는 “라이브러리를 썼다”보다 실패 사례와 수정 근거를 설명한다.

매 단계는 동작하는 기능 → 주요 코드 경로 → 설계 이유 → 실패/평가 결과 → 짧은 설명 연습 순서로 진행한다. 금융 산술 퀴즈로 구현을 멈추지 않는다.
