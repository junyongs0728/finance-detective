# 설계 결정과 대안

현재 코드의 선택 이유와 비용을 정리한다. 효과를 측정하지 않은 선택은 성능 개선으로 표현하지 않는다. 전체 흐름은 [아키텍처](architecture.md), 측정 범위는 [평가 문서](evaluation.md)를 참고한다.

## 1. 수치 계산과 공시 설명을 분리한다

**문제:** 공시 표를 평문으로 바꾸면 열·부호·기간 연결이 사라질 수 있다. 문서에 숫자가 있다는 사실만으로 올바른 계산 입력이라고 볼 수 없다.

**선택:** SEC/DART의 구조화된 수치에 기업·공시·기간·통화·연결 범위를 붙인다. Agent 계산은 이번 요청에서 조회한 Observation ID 두 개를 입력받고 Python `Decimal`로 실행한다. RAG는 서술 근거를 담당한다.

**대안과 한계:** LLM에 표 전체를 전달하는 방법은 더 다양한 항목을 다룰 수 있지만 추출·기간 정합성 검증이 필요하다. 현재 지원 지표는 세 개이며 전용 계정·분기 지원은 제한적이다.

**코드·검사:** [calculate](../src/finance_detective/agents/tools.py), [계산 및 입력 계약 검사](../tests/test_agent_graph.py)의 `test_calculations_use_exact_values_and_reject_invalid_combinations`, `test_tool_args_cannot_inject_numbers_scope_or_unseen_ids`.

## 2. 검색 전에 공시를 고정하고 순위를 결합한다

**문제:** 전체 기업에서 찾은 유사 문장이 다른 회사나 공시의 근거로 섞일 수 있다. 한국어 질문과 영어 공시 사이에는 어휘 차이도 있다.

**선택:** 기업·공시 번호·파서·임베딩 버전으로 `document_id`를 정한다. 해당 문서에서 pgvector 정확 검색과 BM25를 각각 실행하고 RRF로 순위를 결합한다. 현재 후보는 각 30개, 기본 반환은 6개다.

**대안과 한계:** BM25 단독은 어휘 일치가 약한 질문을, 벡터 단독은 고유 용어를 놓칠 수 있어 두 신호를 함께 사용했다. 그러나 같은 정답 집합에서 세 방식을 비교한 우위는 아직 입증하지 않았다. HNSW·reranker도 도입하지 않았다. BM25 통계는 요청마다 Python에서 계산하므로 문서 규모가 커지면 비용을 측정해야 한다.

**코드·검사:** [retrieve](../src/finance_detective/rag/search.py), [dense_rank](../src/finance_detective/rag/store.py), [문서 범위·벡터 순위 검사](../tests/test_rag.py).

## 3. 고정 RAG와 제한된 Agent를 함께 둔다

**문제:** 단순 조회, 문서 설명, 계산과 근거 추적을 같은 모델 루프로 처리하면 필요 없는 호출이 늘어난다.

**선택:** 단순 수치는 Python 경로로 처리한다. 설명 질문에는 비교 가능한 고정 RAG 모드를 제공한다. 기본 복합 분석은 LangChain의 도구 인터페이스와 LangGraph의 상태 루프로 구현했다. 모델은 다음 도구를 선택하고, 서버는 입력·중복 호출·단계·시간·종료 조건을 강제한다. 최종 답변에 계획 모델의 자유 서술을 그대로 쓰지 않는다.

**대안과 한계:** 질문 유형이 좁게 유지된다면 고정 분기만으로도 충분할 수 있다. Agent의 추가 비용·지연 대비 효용은 고정 RAG와 비교 평가해야 한다. 현재 의도 분류는 정규식이며, 수치 전용 Agent 질문도 먼저 공시 준비를 거치는 비용이 남아 있다. 상태는 요청 단위로만 유지한다.

**코드·검사:** [라우팅](../src/finance_detective/chat.py), [실행 루프와 종료](../src/finance_detective/agents/workflow.py), [도구 실행·제한·부분 성공 검사](../tests/test_agent_graph.py).

## 4. 인용 일치와 의미상 근거 검토를 나눈다

**문제:** 유효한 출처를 인용해도 주장의 범위나 원인 설명은 틀릴 수 있다. 반대로 모델이 인용문을 조금 바꾸면 원문 추적이 어려워진다.

**선택:** 모델에는 주장과 원문 구간 ID를 반환하게 하고, 인용문은 서버가 복사한다. 이후 별도 LLM 호출로 주장·인용 문맥을 대조한다. 검토되지 않는 자유 서술 필드가 추가 사실을 전달하지 않도록 제한한다.

**대안과 한계:** 문자열 검사만으로 의미상 오류를 찾을 수 없다. 별도 검토는 비용·지연·과도한 유보를 추가하고 두 모델이 같은 오류를 낼 수도 있다. 따라서 사람의 근거 대조와 독립 평가가 필요하다. 실제 범위 오류와 수정 과정은 [실패 기록](agent-graph-guide.md)에 남겼다.

**코드·검사:** [출처 검증](../src/finance_detective/rag/validation.py), [생성·검토 프롬프트](../src/finance_detective/rag/llm.py), [인용·의미 검토 실패 검사](../tests/test_rag.py).

## 5. PostgreSQL을 기준 기록으로, Neo4j를 관계 조회 PoC로 사용한다

**문제:** 금액만 저장하면 어떤 공시와 원본 항목에 의존하는지 추적하기 어렵다. 같은 지표라도 연도·통화·공시가 다르면 다른 관측값이다.

**선택:** Company·Filing·Period·Metric·Observation·Evidence의 의미와 ID를 명시한다. PostgreSQL 스냅샷을 Neo4j에 멱등 투영하고 조회 결과를 SQL 원본과 대조한다. 수치 원본과 서술문을 구분해 관련성을 인과관계로 저장하지 않는다.

**대안과 한계:** 현재 근거 경로는 SQL JOIN으로도 구현할 수 있다. Neo4j는 경로 질의를 별도 모델로 검증하기 위한 PoC이며 RAG의 필수 구성요소가 아니다. 두 DB 사이 자동 재처리와 속성 이력이 없고, 불일치하면 관계 표시를 중단한다. 복잡한 관계 질의의 효용이 운영 비용을 정당화하지 못하면 SQL로 단순화하는 편이 낫다.

**코드·검사:** [온톨로지](../src/finance_detective/knowledge/ontology.py), [투영·대조](../src/finance_detective/knowledge/graph.py), [멱등성·손상 감지 검사](../tests/test_agent_graph.py).

## 6. 호출 전에 예산을 예약한다

**문제:** 호출 후 비용을 합산하면 동시 요청이 같은 잔여 예산을 각각 사용해 한도를 넘을 수 있다.

**선택:** PostgreSQL 잠금 아래에서 정산액·미확정 예약액·새 호출 예상 상한을 함께 검사한다. 예약을 커밋한 뒤 외부 호출을 실행하고 usage로 정산한다. 청구 여부가 불명확한 실패는 예약을 유지한다.

**대안과 한계:** 전역 예약 잠금은 단순하지만 큰 트래픽에서는 경합이 생길 수 있다. 예상 비용은 실제 청구서와 동일하지 않으며, 불확실한 예약의 복구 절차도 필요하다. 비용·캐시는 사용자와 모델·프롬프트·문서 버전에 연결된다.

**코드·검사:** [비용 예약](../src/finance_detective/rag/billing.py), [동시성·캐시·실패 비용 검사](../tests/test_cost_controls.py), [상세 운영 조건](postgres-cost-guide.md).
